## v3 comparison (2026-09-03)

Same 64-measure string quartet, 20 calls in Edge headless. New layout includes
metadata, annotation lanes and page allocation. Timings are wall-clock samples,
not stable CI assertions.

| Path | 20 renders, ms |
| --- | ---: |
| Original renderer | 54.0 |
| v3 forced full rendering (cache disabled) | 369.0 |
| v3 revision cache (one full render + 19 reuses) | 18.8 |

The actual app opts into revision caching. Repeated unchanged rendering is 65.2%
below the original 20-render baseline. This is not a claim that new full layout is
faster: cold layout has more work and remains a future optimization target.
Selecting a note invokes E.render zero times and schedules no autosave, verified
with an actual pointer click. Raw model consumers may use uncached rendering;
cache users must edit via core.mutate/core helpers or call core.invalidate.

## Phase 4 후 재생 메모리 (4-4)

자동으로 확인한 것: **악보를 몇 번 바꿔도 살아 있는 샘플 악기 수 = 지금 악보의 연주 파트 수** (`tests/playback-lifecycle.test.mjs`). 피아노 악보 A → 피아노 악보 B(다른 파트 ID) → 현악 악보 C(+드럼 파트)를 세 바퀴 돌려도 `debugStats()`의 `instances`는 연주 파트 수, `buses`는 파트 수와 같고, 지난 악보의 악기는 정확히 한 번씩 `dispose`되며, `loaders`는 쓰는 Splendid 종류 수(고음질 피아노가 있을 때만 1)를 넘지 않는다. 기본 음질과 고음질 두 경우 모두 확인했다.

아래 표는 **사람이 채운다**(실제 브라우저의 작업 관리자 값은 자동으로 읽을 수 없다). 같은 PC·같은 Chrome에서 같은 순서로 재야 비교할 수 있다.

**D-3 절차**: 새 시크릿 창 → 앱 열기 → Chrome 작업 관리자(Shift+Esc)에서 이 탭의 메모리 값 → **A** → 데모 "나비야"(파일 ▸ 데모)를 끝까지 재생 → **B** → 다른 데모를 열어 재생하기를 3번 → **C1·C2·C3**. 각 시점마다 개발자도구 콘솔에서 `SF.playback.debugStats()`를 같이 적는다. 두 번 잰다: ① 설정을 건드리지 않은 기본 음질, ② 설정 ▸ 피아노 음질 ▸ 고음질(약 19MB)로 바꾼 뒤(시크릿 창을 새로 열어 다시 시작).

| 시점 | 리팩토링 전 | Phase 4 후 — 기본 음질 | Phase 4 후 — 고음질 | `debugStats()` instances / loaders / buses |
|---|---:|---:|---:|---|
| A 앱을 연 직후 | | | | |
| B 나비야 재생 직후 | | | | |
| C1 다른 데모 재생 (1회) | | | | |
| C2 (2회) | | | | |
| C3 (3회) | | | | |

판정(설계서 8장): C3 − B ≤ 약 +50MB(목표, 실측 후 조정) · 로딩 중 200ms를 넘는 Long Task 0~1개(Chrome 성능 패널, 목표) · 모든 시점에서 `instances` = 지금 악보의 연주 파트 수. "리팩토링 전" 열은 `git switch --detach v3.0.1-baseline`로 같은 방법으로 잰 값(`debugStats()`는 이 시점에 없으니 메모리 값만).

## Phase 5 후 편집 지연 (5-B1·5-B2)

같은 방법(`node tests/perf-edit.mjs`, 피아노 2단 100마디·8분음표 1,600개에서 음표 입력 1회의 지연 = 입력 + 즉시 갱신, 10회 측정의 중앙값·최댓값)을 한 세션 안에서 앞뒤로 번갈아 3회씩 쟀다. **다른 날의 값끼리는 비교하지 않는다** — 같은 코드도 환경에 따라 ±30% 흔들린다(예: 이 세션에서 리팩토링 전 master 코드는 중앙값 373~436ms로, 처음 기준 306ms보다 느리게 나왔다).

| 측정(같은 세션, 번갈아 3회) | 중앙값(3회) | 중앙값 3회 값 | 최댓값 3회 값 |
|---|---:|---|---|
| 리팩토링 전 master(016ad44) | 430ms | 430·436·373 | 516·600·573 |
| 5-B1 전(= P5-A1·A2 병합 직후) | 331ms | 376·331·321 | 482·505·406 |
| **5-B1 후**(relayout 후처리를 data-ref Map 한 번 훑기로) | **220ms** | 220·295·216 | 332·433·380 |

5-B1은 편집 한 번의 지연을 이 환경에서 약 1/3(331 → 220ms) 줄였다. 5-B2(클릭 영역을 조판기가 직접 그림)의 값은 아래에 이어서 적는다.

### 5-B2 (클릭 영역을 조판기가 직접 그림) — 세 코드를 한 번에 재서 비교

5-B1 전(`P5-A2` 병합 직후), 5-B1 후(= 5-B2 전, `phase/p5-stems-render`), 5-B2 후(작업 트리)를 **같은 세션에서 세 코드를 번갈아** 3회씩 쟀다(코드마다 따로 띄운 서버를 `SF_URL`로 가리킴). 위 표와는 다른 때에 잰 값이라 같은 코드도 값이 다르다(5-B1 후: 위 표 220ms ↔ 아래 240ms) — **위 표의 값과 섞어 비교하지 않는다.**

| 측정(같은 세션, 번갈아 3회) | 중앙값(3회) | 중앙값 3회 값 | 최댓값 3회 값 |
|---|---:|---|---|
| 5-B1 전(P5-A2 병합 직후) | 347ms | 347·346·361 | 534·433·423 |
| 5-B1 후(= 5-B2 전) | 240ms | 240·224·278 | 348·375·530 |
| **5-B2 후**(app.js 후처리 삭제, 조판기가 .note-hit을 그림) | **236ms** | 209·236·284 | 325·356·414 |

읽는 법: 편집 지연을 줄인 것은 5-B1(347 → 240ms, 약 31%)이고, **5-B2는 5-B1과 차이가 측정 오차 안(240 → 236ms)이다.** 5-B2의 목적은 속도가 아니라 구조(클릭 영역을 만드는 곳을 조판기 한 곳으로 모으고, 내보내기에는 절대 들어가지 않게 함)이며 지연이 나빠지지 않았다는 것을 확인한 것이다.

5-B2 후 값은 세 번 모두 300ms 미만이다 → 설계서 13장 9-8(증분 조판)은 **Phase 9의 원래 자리를 유지**한다(docs/DECISIONS.md P5 줄). 이 값은 클라우드 작업 환경 기준이다. 사람 PC에서 `node tests/perf-edit.mjs`(또는 D-3 절차)로 같은 방법으로 재서 중앙값이 300ms 이상이면 DECISIONS의 P5 줄을 "9-8을 Phase 8 앞으로"로 바꾼다.

## Phase 7-A1 후 MIDI 가져오기 (일괄 입력)

`node tests/bench-midi.mjs 1000 2000 4000 10000`(8분음표 N개, 템포 120, 격자 1/16)을 같은 세션에서 3회 쟀다. `convertMs`는 `midiToScore`(변환)만의 시간이고, `indexBuilds`는 그동안 `eventIndex`가 악보 전체 색인을 새로 만든 횟수다. 위 "리팩토링 전 기준 (016ad44)" 표와 같은 환경(Node 22, 클라우드 샌드박스)이지만 다른 때에 잰 값이라 ±20% 흔들린다.

| 음 개수 | 리팩토링 전(`convertMs`) | 7-A1 후 — 중앙값(3회) | 7-A1 후 — 3회 값 | 인덱스 재구축(전 → 후, 전은 옛 코드에 계수기를 임시로 달아 샌 값) |
|---:|---:|---:|---|---|
| 1,000 | 1,335ms | **82ms** | 69·82·90 | 1,001회 → 1회 |
| 2,000 | 3,524ms | **146ms** | 146·124·157 | 2,001회 → 1회 |
| 4,000 | 13,119ms | **209ms** | 209·169·212 | 4,001회 → 1회 |
| 10,000 | 108,914ms(1회) | **430ms** | 386·430·520 | (옛 코드는 109초가 걸려 세지 않았다 — 위 세 줄이 모두 "음 개수 + 1"회) → 1회 |

목표 "1만 음 2초 이하" ✅(0.4~0.5초). 결과는 골든 해시와 37가지 입력·옵션 행렬(`tests/midi-golden.test.mjs`)로 구현 전과 똑같음을 확인했다.
복잡도는 시간 대신 횟수로 지킨다(`tests/audioio-v3.test.mjs`, 계수기 `C.__stats`). 4,000음에서 센 값: 인덱스 재구축 **4,001 → 1회**(시험 기준 ≤ 2), 악보 전체 타이 정리 **4,001 → 1회**(≤ 2), 마디 길이 표 계산 **4,503 → 503회**(음 4개당 1번 이하 = 1,000회 이하; 남은 약 500회는 준비 단계에서 마디마다 한 번쯤 다시 계산하는 것이고 음마다가 아니다). 앞 값은 7-A1 구현을 일부러 옛 방식(음마다 `inputAt` + `findEvent`)으로 되돌린 변형에서 센 것이다.
**7-A2(일괄 빌더)는 필요 없다**: 1만 음이 0.4~0.5초라 시작 조건("7-A1 뒤에도 실제 곡에서 2초를 넘을 때만")에 해당하지 않는다. 실제 곡 파일(사람이 가진 .mid)의 시간은 (P7-A1) 사람 확인 항목에 적어 둔다.

## Phase 7-B2 후 실행 취소 기록 (메모리 예산)

`node --expose-gc tests/bench-history.mjs`로 쟀다. 악보에 "템포 바꾸기" 편집을 200번 하면서 실행 취소 기록이 차지하는 메모리(강제 가비지 수집 뒤의 힙 증가)와 편집 1번의 비용을 옛 방식(악보 객체를 `structuredClone`으로 200개 복사)과 새 방식(압축 JSON 글자 + 48MB 예산, `C.mutate` 전체)을 같은 악보로 비교한다. 두 번 돌려 같은 값이 나왔다.

| 악보 | 방식 | 기록 개수 | 힙 증가 | 편집 1번 |
|---|---|---:|---:|---:|
| quartet64(64마디 사중주) | 옛: 객체 복사 200개 | 200 | 67.2MB | 복사만 2.2ms |
| quartet64 | **새: 글자 기록 + 48MB 예산** | **189** | **47.9MB** | **3.5ms**(mutate 전체) |
| 피아노 100마디(1,600음) | 옛: 객체 복사 200개 | 200 | 140.8MB | 복사만 4.5ms |
| 피아노 100마디 | **새: 글자 기록 + 48MB 예산** | **91** | **47.9MB** | **6.8ms**(mutate 전체) |

기록 글자 총길이(완료 기준 측정): quartet64는 편집 200회 뒤 **25,050,180자**(항목당 132,541자 × 189개 = UTF-16 추정 47.8MB — 설계서의 참고 측정 132,246자와 같은 수준), 피아노 100마디는 25,081,025자(항목당 275,616자 × 91개). 둘 다 예산 48MB(= 25,165,824자)에서 멈춘다.

읽는 법:
- 옛 방식의 기록 메모리는 악보가 클수록 그대로 늘어난다(피아노 100마디에서 이미 141MB, 더 큰 악보는 더 큼). 새 방식은 **어떤 악보에서도 약 48MB에서 멈춘다.** 대신 아주 큰 악보에서는 되돌릴 수 있는 횟수가 200번보다 줄어든다(quartet64 189번, 피아노 100마디 91번). 가장 가까운 1번은 예산과 상관없이 늘 남긴다.
- 편집 1번의 비용은 1~3ms 늘었다(JSON 만들기가 객체 복사보다 느리다). 실제 편집 지연(`tests/perf-edit.mjs`, 1,600음 피아노 100마디, 3회 중앙값)은 **변경 전 206·189·171ms → 변경 후 202·191·186ms**(최댓값 258·312·342 → 321·283·319ms)로 차이가 측정 오차 안이다. 편집 지연의 대부분은 다시 그리기(조판)다.
- 실행 취소 한 번의 복원 시간은 옛 방식과 같거나 짧다(Node 단독 측정: quartet64 9.7 → 8.9ms, 피아노 100마디 12.7 → 9.9ms. 스냅샷 만들기는 2.6 → 3.6ms, 5.8 → 9.2ms).
- 이 값은 클라우드 작업 환경 기준이다. 사람의 기기(특히 휴대폰)에서 큰 악보로 실행 취소를 눌러 보는 일은 `docs/REFACTOR_LOG.md`의 사람이 할 일 `(P7-B2)`에 적었다.
